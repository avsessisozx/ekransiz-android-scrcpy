Control a Screenless Android Phone from a PC with adb + scrcpy

Redmi Note 10 Pro (sweet / M2101K6G) · OrangeFox R12.1_3 · Android 13 · 2026-11-07

Scope: your own device, or a device you are authorized to service. The procedure does not bypass the lockscreen credential; it only opens an interaction window for a device whose display is physically gone.

Summary

A phone whose display panel has been removed can still be used from a PC with adb + scrcpy. The hard part is not scrcpy — it is getting adb to come up on a device whose ROM disables USB debugging at boot and whose screen cannot confirm the “Allow USB debugging” dialog.

This write-up shows the full path on a Redmi Note 10 Pro:

  1. root adb inside OrangeFox recovery (ro.adb.secure=0),
  2. pre-seeding the host key in /data/misc/adb/adb_keys,
  3. why editing settings_global.xml does not stick (the ROM rewrites it at boot),
  4. the working fix: an init script in /system/etc/init that sets adb_enabled=1 at sys.boot_completed,
  5. scrcpy over USB.

Result: adb is back about 20 seconds after every boot, and the PC can mirror and control the phone while the cable is attached.

1. The problem

The display assembly is physically missing, so there is no touch input either. When the phone boots into Android, it enumerates as MTP only (VID_2717&PID_FF40) — no ADB interface. The lockscreen is a pattern and is FLAG_SECURE, so screen capture of the credential UI is blocked.

Goal: get the phone back into normal use and control it from the PC.

4. Step by step

4.1 Root adb in recovery

With the phone off, hold Power + Volume Up to enter OrangeFox. Recovery adbd runs with ro.adb.secure=0, so any host gets a root shell:

adb devices -l
# db7ea5d1  recovery  product:sweet model:M2101K6G
adb shell id
# uid=0(root) ... context=u:r:su:s0

4.2 Check verity before touching /system

adb shell 'avbctl get-verity'          # verity is disabled.
adb shell 'avbctl get-verification'    # verification is disabled.
adb shell 'mount | grep dm-0'
adb shell 'cat /proc/cmdline'

On this device the vbmeta header reported flags=0x3 (HASHTREE_DISABLED | VERIFICATION_DISABLED), so writing to /system does not break the boot.

4.3 Pre-seed the host key

You cannot tap “Allow USB debugging” on a missing screen, so the PC key is written in advance:

# only the first token (base64) of adbkey.pub — no "user@host"
adb push adbkey.clean /data/misc/adb/adb_keys
adb shell 'chmod 640 /data/misc/adb/adb_keys'
adb shell 'chown system:shell /data/misc/adb/adb_keys'
adb shell 'chcon u:object_r:adb_keys_file:s0 /data/misc/adb/adb_keys'

Owner (system:shell), mode (0640) and the SELinux label (adb_keys_file) all matter; otherwise adbd will not read the key.

4.4 First attempt: editing settings_global.xml (and why it failed)

The obvious approach is to flip adb_enabled in /data/system/users/0/settings_global.xml:

<setting id="39969" name="adb_enabled" value="0" package="android" defaultValue="0" defaultSysSet="true" />

After the edit the value is 1 on disk — but on the next boot the file is rewritten by SettingsProvider: the value is back to 0, and the row id changes every boot (observed: 39969 → 60862 → 60864). Even sync before rebooting did not help. The setting simply does not survive this ROM’s boot.

4.5 The fix: an init script that runs at boot

The setting has to be applied after boot completes. Android’s init parses /system/etc/init/*.rc, so a small script is enough.

/system/etc/adb_boot.sh:

#!/system/bin/sh
i=0
while [ $i -lt 20 ]; do
  settings put global adb_enabled 1 && break
  sleep 2
  i=$((i+1))
done
setprop sys.usb.config mtp,adb

/system/etc/init/adb_boot.rc:

service adb_boot /system/bin/sh /system/etc/adb_boot.sh
    class late_start
    user root
    group root
    seclabel u:r:su:s0
    oneshot
    disabled

on property:sys.boot_completed=1
    setprop sys.usb.config mtp,adb
    start adb_boot

Set permissions and labels, then sync and reboot:

adb shell 'chmod 0755 /system/etc/adb_boot.sh && chmod 0644 /system/etc/init/adb_boot.rc'
adb shell 'chown root:root /system/etc/adb_boot.sh /system/etc/init/adb_boot.rc'
adb shell 'chcon u:object_r:system_file:s0 /system/etc/adb_boot.sh /system/etc/init/adb_boot.rc'
adb shell sync
adb reboot

About 20 seconds after boot, adb devices shows the phone as device and settings get global adb_enabled returns 1.

Why both lines? setprop sys.usb.config mtp,adb triggers the Qualcomm USB init block that switches the PID to FF48 (MTP+ADB), while settings put makes UsbDeviceManager keep adb in the configuration.

4.6 scrcpy

scrcpy -s db7ea5d1 --max-size 1200 --no-audio
  • The screen appears on the PC; mouse = touch, keyboard = text/PIN.
  • Input is injected through ADB, so it works even though the touch panel is gone.
  • 1080×2400 over USB 2.0 is smoother with --max-size 1200.

5. The lockscreen: FLAG_SECURE and the “freeze”

The pattern/PIN screen is marked FLAG_SECURE. Android blocks screenshots and screen capture there:

SurfaceFlinger: FB is protected: PERMISSION_DENIED
screencap: rc=1 (0 bytes)

So scrcpy shows the last frame and appears frozen while the credential UI is up. Input is not blocked:

  • you can type the PIN or draw the pattern blind (keyboard or input motionevent);
  • or remove the credential entirely if you know it:
adb shell 'locksettings clear --old <pattern>'

The 3×3 grid is numbered like a classic keypad (1 2 3 / 4 5 6 / 7 8 9); --old is the dot sequence. To keep the lock but stop it from re-engaging:

adb shell 'settings put system screen_off_timeout 2147483647'
adb shell 'settings put secure lock_screen_lock_after_timeout 86400000'
adb shell 'svc power stayon true'

6. Why AI assistants refuse — and the framing lesson

During this work an AI assistant refused the request. The reason was not the task itself but the vocabulary: earlier messages contained locksettings.db, gatekeeper, CE encryption, sendevent — a combination that reads like a lockscreen-bypass chain. The model cannot tell “recovering my own device” from “accessing someone else’s device” out of that text alone, so it stops.

When the same task was stated plainly — “my own phone, the screen is gone, I want to use scrcpy” — the assistant offered help.

The lesson is about context, not capability. Description matters: a technical transcript that mentions locks, encryption and input injection will be treated as high-risk until the legitimate context is explicit.

7. Risks, limits, rollback

  • Verity enabled? Modifying /system can break the boot. Check avbctl get-verity first.
  • ROM update / factory reset removes the init script and adb_keys; redo the setup.
  • USB instability was frequent on this device; try another cable/port and disable Windows “USB selective suspend”.
  • Rollback: delete /system/etc/adb_boot.sh and /system/etc/init/adb_boot.rc, then sync and reboot.
  • Security: adb_keys + adb_enabled=1 gives anyone with physical cable access a shell. Only keep it on a device you control.
